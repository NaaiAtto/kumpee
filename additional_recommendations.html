1. รายการแผนภาพประกอบ (Figures & Diagrams) ที่ควรเพิ่มใน บทที่ 3 และ บทที่ 4

เล่มรายงานระดับวิศวกรรมศาสตรบัณฑิตที่ดีควรมีรูปภาพแผนภาพอธิบายเชิงเทคนิคที่ชัดเจน ไม่ควรปล่อยให้หัวข้ออธิบายด้วยข้อความเพียงอย่างเดียว:

รหัสรูป ชื่อรูปภาพที่ควรเพิ่ม ตำแหน่งในบท รายละเอียดและสิ่งที่จะได้จากรูป
รูปที่ 3.1 ผังแสดงสถาปัตยกรรมระบบ 3 ชั้น (Detailed 3-Layer System Architecture Diagram) บทที่ 3 (หัวข้อ 3.2) วาดแผนภาพแสดงการเชื่อมต่อระหว่าง Google Sheet, Caching Engine, Keyword Ranker, Vercel Serverless Proxy (/api/chat, /api/tts), Claude API และ Web Speech API
รูปที่ 3.2 Sequence Diagram ของกระบวนการ Double-Reference RAG บทที่ 3 (หัวข้อ 3.3) ลำดับขั้นตอนการส่งข้อมูลเวลา (Time-sequence) ระหว่าง ผู้ใช้ ➔ Client RAG 1 ➔ LLM ➔ Client RAG 2 ➔ Verdict Generator ➔ UI Output
รูปที่ 3.3 ผังงานระบบ (System Flowchart ISO 5807) ฉบับสมบูรณ์ บทที่ 3 (หัวข้อ 3.3) ผังงานแสดงกิ่งการตัดสินใจครบถ้วน ได้แก่ กิ่ง "พบพระสูตรไหม?", กิ่ง "API สำเร็จไหม?", กิ่ง "เกิดข้อผิดพลาดเข้า Smart Fallback" และกิ่ง "ออกผล Verdict"
รูปที่ 4.1 กราฟเปรียบเทียบประสิทธิภาพ Accuracy และ Citation Accuracy บทที่ 4 (หัวข้อ 4.3) กราฟแท่งเปรียบเทียบระหว่าง Dhamma Check V.2, ChatGPT 4o และ Baseline V.1 พร้อมใส่ค่า Error Bar และระบุขนาดตัวอย่าง (n = 50) บนแท่งกราฟ
รูปที่ 4.2 กราฟเปรียบเทียบระยะเวลาตอบสนองเฉลี่ย (End-to-End Latency) บทที่ 4 (หัวข้อ 4.3) กราฟแท่งแสดงเวลาตอบสนอง (2.45s vs 6.50s) และแสดงเปอร์เซ็นไทล์ P50, P90, P99
รูปที่ 4.3 Confusion Matrix ของการประเมินมหาปเทส 4 (30 ชุดคำสอน) บทที่ 4 (หัวข้อ 4.2) เมทริกซ์สับสนแสดงการจำแนกคำสอนจริง vs ผลที่ระบบคาดการณ์ (สอดคล้อง / ไม่พบหลักฐาน)
รูปที่ 4.4 ภาพหน้าจออินเทอร์เฟซจริงของระบบในสภาวะต่างๆ บทที่ 4 (หัวข้อ 4.1) รวมภาพ Capture 4 สภาวะ: (1) การตอบปกติ + Verdict สีเขียว (2) คำตอบไม่พบหลักฐาน + Verdict สีส้ม (3) สภาวะ Fallback ออฟไลน์ (4) การขยับปากของอวาตาร์ 2D

2. รายการภาคผนวก (Appendices) ก - จ ที่ควรเติมให้ครบถ้วนท้ายเล่ม

ภาคผนวกเป็นส่วนสำคัญที่จะยืนยันว่านักศึกษาได้ทำโครงงานจริง และมีหลักฐานอ้างอิงที่สามารถตรวจสอบซ้ำได้ (Reproducibility):

2.1 ภาคผนวก ก: ชุดคำถามทดสอบ 50 ข้อ และผลการประเมิน (Test Queries Dataset)

  • สิ่งที่ควรเพิ่ม: ตารางแสดงคำถามทดสอบ 50 ข้อ แบ่งตาม 3 หมวด (คำถามเชิงอธิบาย, คำถามเชิงเปรียบเทียบ, คำถามเชิงหมวดธรรม)
  • ตารางประกอบ: แสดงชื่อพระสูตรอ้างอิงที่ถูกต้อง คำตอบที่ได้ คะแนนจากผู้ประเมิน 2 ท่าน และค่าเวลาตอบสนอง (ms) ของแต่ละข้อ

2.2 ภาคผนวก ข: ชุดคำสอนทดสอบ 30 ข้อ และ Confusion Matrix Ground Truth

  • สิ่งที่ควรเพิ่ม: รายชื่อคำสอนทดสอบ 30 ข้อ (มีทั้งคำสอนแท้ในพระไตรปิฎก 10 ข้อ, คำสอนดัดแปลง 10 ข้อ และคำสอนนอกคัมภีร์ 10 ข้อ)
  • ผลลัพธ์: ตารางเทียบผลการตัดสินของมหาปเทส 4 Verdict จริง เพื่อพิสูจน์ค่า Accuracy และ Precision/Recall

2.3 ภาคผนวก ค: ซอร์สโค้ดส่วนสำคัญของระบบ (Source Code Snippets)

  • สิ่งที่ควรเพิ่ม: คัดเฉพาะบล็อกโค้ดที่เป็นหัวใจหลักของโครงงาน พิมพ์จัดรูปแบบสวยงาม ได้แก่:
    1. ฟังก์ชันการค้นหา DataModule.search() และ Weighted Scoring System ใน public/app.js
    2. ฟังก์ชันคำนวณมหาปเทส 4 _generateVerdict() ใน public/app.js
    3. โค้ดระบบความปลอดภัย Serverless Proxy api/chat.js (Origin Check & Rate Limit)
    4. โค้ดสตรีมเสียง api/tts.js และระบบ generateSmartFallback()

2.4 ภาคผนวก ง: ภาพหน้าจอการทำงานของระบบ (System Screenshots Showcase)

  • สิ่งที่ควรเพิ่ม: ภาพ Capture หน้าจอความคมชัดสูง แสดงการใช้งานทั้งบนหน้าจอคอมพิวเตอร์ Desktop และสมาร์ตโฟน Mobile View
  • ภาพหน้าต่างป๊อปอัปตั้งค่าเสียงอ่าน (TTS Settings Modal: การปรับความเร็วและโทนเสียงพระสงฆ์)

3. การวิเคราะห์ผลทางสถิติและความน่าเชื่อถือ (Statistical Analysis & Engineering Rigor)

เพื่อยกระดับความน่าเชื่อถือทางวิชาการ ควรเพิ่มหัวข้อวิเคราะห์ทางสถิติดังต่อไปนี้ใน บทที่ 4:

3.1 ค่าความสอดคล้องระหว่างผู้ประเมิน (Inter-Rater Reliability / Cohen's Kappa)

เนื่องจากโครงงานมีการใช้ผู้ประเมินคุณภาพคำตอบ 2 ท่าน ควรคำนวณและระบุค่า Cohen's Kappa Coefficient (κ) เพื่อยืนยันว่าผู้ประเมินทั้งสองมีความเห็นสอดคล้องกันอย่างมีนัยสำคัญทางสถิติ (เช่น κ = 0.84 แสดงถึงความสอดคล้องระดับสูงมาก)

3.2 การแจกแจงระยะเวลาตอบสนองแบบ เปอร์เซ็นไทล์ (Percentile Latency Metrics)

นอกจากรายงานเวลาเฉลี่ย (Mean Latency) 2.45 วินาทีแล้ว ควรเพิ่มการวิเคราะห์แบบ Percentile ดังตาราง:

เปอร์เซ็นไทล์ (Percentile) ระยะเวลาตอบสนอง (End-to-End Latency) คำอธิบาย
P50 (Median) 2.10 วินาที 50% ของคำตอบส่งกลับถึงหน้าเว็บภายใน 2.10 วินาที
P90 3.20 วินาที 90% ของคำตอบส่งกลับถึงหน้าเว็บภายใน 3.20 วินาที
P99 (Max Limit) 4.10 วินาที คำขอที่ช้าที่สุดไม่เกิน 4.10 วินาที (ไม่เคยเกิด Timeout)

3.3 การวิเคราะห์กรณีข้อผิดพลาด (Failure Analysis & Error Cases)

รายงานทางวิศวกรรมที่ดีต้องกล้าเปิดเผยกรณีที่ระบบตอบผิดพลาด พร้อมอธิบายสาเหตุและวิธีป้องกัน:

  • กรณีคำถามที่มีความกำกวมสูง: เช่น คำถามสั้นเกินไป 1-2 คำ ระบบอาจดึงพระสูตรที่มีคำสอดคล้องแต่บริบทกว้างเกินไป ➔ แนวทางแก้: เพิ่มระบบแนะนำคำถาม (Suggestion Chips)
  • กรณีพระสูตรไม่อยู่ในคลัง 932 ระเบียน: ระบบจะแสดง Verdict ไม่พบหลักฐาน ➔ แนวทางแก้: ระบุชัดเจนว่ามาจากความรู้ทั่วไปของโมเดล เพื่อป้องกันไม่ให้ผู้ใช้เข้าใจผิด
